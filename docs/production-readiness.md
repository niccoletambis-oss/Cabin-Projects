# Production readiness — Phase 4

Phase 4 prepares deployment. It does not deploy, select a domain/provider, enable MFA, or erase the existing development database. The application remains a private staff system. Complete the staging acceptance steps below before opening production traffic.

## Environments and secrets

Copy `.env.example` for **local development only** (`APP_ENV=development`). Use an isolated PostgreSQL database and `APP_ENV=test` in CI. A local optimized build may still use development configuration; `NODE_ENV=production` describes Next's optimization, while `APP_ENV` describes the deployment. In real hosting explicitly set `APP_ENV=production`; missing `APP_ENV` defaults to production when Node is production. Do not set a deployed production service to development to bypass validation.

Startup instrumentation rejects missing/invalid critical production configuration without printing values. No secrets use the browser-visible `NEXT_PUBLIC_` prefix. Keep runtime secrets in a hosting secret manager, not Git, Docker layers, build arguments, frontend configuration, URLs in command history, or CI logs. The standalone preparation step excludes/removes traced `.env` files and copies static assets. Build with placeholder development configuration, supply real values at runtime.

| Required production variables                                                                 | Purpose                                                                                            |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `APP_ENV=production`, `APP_URL=https://<chosen-domain>`                                       | Canonical origin, fixed redirects and reset links; no path/query/userinfo                          |
| `DATABASE_URL`, `DATABASE_SSL=verify-full`                                                    | PostgreSQL application connection with certificate verification                                    |
| `SECURITY_HASH_KEY`                                                                           | Independent 32-byte random hex HMAC key for hashed limiter/audit subjects (`openssl rand -hex 32`) |
| `FILE_STORAGE_PROVIDER=s3`, `FILE_STORAGE_BUCKET`, `FILE_STORAGE_REGION`                      | Private object storage                                                                             |
| `FILE_STORAGE_ACCESS_KEY` + `FILE_STORAGE_SECRET_KEY` **or** `FILE_STORAGE_USE_IDENTITY=true` | Scoped service key pair or explicitly selected SDK workload identity                               |
| `EMAIL_PROVIDER=smtp`, `SMTP_HOST`, `SMTP_PORT` (465 or 587), `SMTP_FROM`                     | Recovery email; TLS/STARTTLS with certificate validation                                           |
| `SMTP_USER` + `SMTP_PASSWORD` **or** `SMTP_USE_IDENTITY=true`                                 | SMTP authentication or explicit trusted relay; the flag does not implement provider-specific OAuth |
| `TRUST_PROXY=true`, `TRUSTED_CLIENT_IP_HEADER=x-cabin-client-ip`                              | Dedicated header overwritten by the only trusted reverse proxy                                     |

Optional settings are listed in `.env.example`: direct migration connection, database/SMTP custom CA paths, pool/timeouts, session hours, S3-compatible HTTPS endpoint/path style/KMS key, monitoring webhook/token, rate limits, and offline backup/admin command inputs. `APP_ORIGIN` remains a compatibility alias and must agree with `APP_URL`. `SESSION_SECRET` is intentionally unused: sessions contain random opaque 256-bit tokens and only SHA-256 digests are stored. HMAC key rotation invalidates outstanding limiter windows/subject correlations, not sessions. Rotate database, object-storage, SMTP and monitoring credentials independently through the secret manager.

All development/sample seeds reject **either** `APP_ENV=production` or `NODE_ENV=production`. `db:seed:production` validates production configuration and intentionally creates nothing. Production migrations and explicit admin bootstrap replace sample seeding. Never copy demo `.example` accounts/passwords or synthetic guest records into production. `production:check` rejects demo/test-domain and active passwordless accounts, checks the database and private bucket, and must run against the intended production configuration.

## Database and migration release

Use managed PostgreSQL 17 or a maintained compatible release, separate least-privilege application and migration roles, verified TLS, network-restricted ingress, encrypted disks and automated provider backups. The app uses `DATABASE_POOL_MAX=10` by default with 5-second connection timeout, 30-second idle timeout and a 15-second statement timeout. Size instances × pool maximum below the provider limit, reserving connections for migrations, recovery and monitoring. A transaction-pooling proxy can serve application connections; set `DIRECT_DATABASE_URL` for migrations/backup tools. Prisma schema-engine TLS options differ from libpq: `prisma.config.ts` forces `sslmode=require&sslaccept=strict` in production and maps `DATABASE_SSL_CA_FILE` to its `sslcert` option. Merely passing libpq’s `sslmode=verify-full` to this Prisma CLI version did not reject the local non-TLS database; the supported require/strict combination did. The application and native backup clients use verified TLS independently. Application connection URL options cannot disable certificate validation.

Release from a private tooling checkout with Node 24 and `npm ci` (including development tools). Never run migrations from a public browser route:

```sh
npm run db:generate
npx prisma validate
npx prisma migrate status
npm run db:deploy
```

Review migration SQL and take a verified backup first. Only forward migrations are supported; never run `migrate reset`, `db push --accept-data-loss`, drop schemas, or use production as a shadow database. Verify drift with `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code`. Custom SQL CHECK constraints remain migration-owned and must also be reviewed because Prisma's schema diff does not model them.

Migration `20261029030000_production_foundation` adds `StoredFile`, `PrivateAttachment`, `PasswordResetToken`, `RateLimitBucket`, storage provider/state enums, nullable legacy attachment file references, booking privacy archive/legal hold fields, and activity request IDs. Checks enforce positive file sizes/rate counts and exactly one private-evidence parent. Existing bytes and histories remain intact. Indexes support inventory name ordering, booking status/arrival, damage status/date and booking lookup, expense dates/author, charge status/date, audit actor/date, reset expiry, storage state/creator and rate expiry. Existing booking dates, inspection booking/room and linen date/item/location indexes remain. The inventory name B-tree supports ordering; arbitrary substring searches are not claimed to use it. Consider measured trigram indexing only if larger data/query plans justify it.

Receiving, stock moves, audit review, linen transfers, inspection completion, expenses and guest-charge transitions retain their transaction/row-lock/idempotence protections. Files stage before a record transaction; its metadata becomes READY in the same transaction as the attachment link. Rollback safely discards staged bytes. Cleanup never removes a READY object after an ambiguous commit.

## Password recovery, sessions and account recovery

Public pages: `/forgot-password`, `/reset-password?token=…`. POST endpoints: `/api/password/forgot`, `/api/password/reset`. Every submission requires a matching canonical Origin and Host and a bounded URL-encoded body. Known/unknown requests return the same message and redirect; email delivery runs after the response with a minimum request duration. Account rate limits apply equally to known/unknown emails. New requests invalidate previous pending links.

Tokens contain 32 random bytes, expire in 30 minutes, and are stored only as SHA-256 hashes. Each is bound to the password hash at issuance. The reset uses a user lock and conditional claim, so concurrent submissions succeed once. Success clears temporary login lockout and revokes every session and pending recovery token. Password/account changes also revoke sessions and pending reset links. Existing password verification remains compatible; new passwords require 15–128 characters and salted scrypt (N=32768, r=8, p=3).

Configure any TLS-capable SMTP provider/relay, verify the sender domain and SPF/DKIM/DMARC, then send a staging recovery email and follow it on a phone. The app does not require a paid service. SMTP has timeouts, certificate verification and no debug logging. With no SMTP, local loopback development may explicitly set `DEV_RESET_LOG=true`; this is rejected in production and never logs reset URLs in tests. Do not enable it in a shared development environment. Queued email is not durable: a process termination can lose an in-flight message; requesting a new link safely retries. A durable mail queue is a future enhancement.

Sessions expire after 8 hours by default (configurable 1–24). Cookies are HttpOnly, SameSite=Lax, path `/`, Secure in production/HTTPS. Deactivated users and expired/revoked sessions cannot authenticate. Five failed attempts temporarily lock an account for 15 minutes; attempts during the lock do not extend it. Successful authentication after expiry resets the counter. Login failures remain generic.

Initial admin, from private release tooling with migrations already applied:

1. Create a private `0600` file holding a unique strong password, supplied through a secret manager/private editor. Do not put it in shell arguments/history.
2. Set `ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD_FILE` and run `npm run admin:bootstrap`.
3. Bootstrap serializes with user management and refuses if any Admin already exists. Remove the temporary password file through your secret manager.
4. Offline recovery requires an existing Admin email, the same inputs with a new private password file, and exact `ADMIN_RECOVERY_CONFIRM=RECOVER_ADMIN:<email>`, then `npm run admin:recover`. It unlocks/reactivates only that Admin, revokes all its sessions/reset tokens, and audits the action. Protect this CLI with database/host operator access; it is a break-glass tool, not a public setup endpoint.

MFA activation is **deferred**. `MFA_MODE=disabled` is the only supported setting; any other policy fails startup/login rather than bypassing a challenge. The verifier interface is an extension boundary. Phase 5 must ship encrypted TOTP secrets using a separately rotated KMS-backed key, password-confirmed pending enrollment with proof before activation, one-time hashed recovery codes, replay/time-window and challenge rate controls, code rotation, password-confirmed disable/re-enrollment, security events and an independently tested offline recovery process together. There is no misleading “enabled” UI or partially active MFA.

## Private file storage

`ObjectStorage` defines put/get/delete/health. The development adapter stores durable bytes in PostgreSQL, never ephemeral files. Production uses the official S3-compatible SDK with private server-mediated access, HTTPS, request timeouts, optional configured proxy/CA trust, scoped credentials or SDK identity, and SSE-S3 AES256 (or `FILE_STORAGE_KMS_KEY`). Configure an existing private bucket; the app never creates a public bucket or generates public object URLs. Keep the bucket/region stable while rows reference that deployment. Changing provider or bucket requires an explicit verified migration, not an environment-only switch.

Provision a dedicated bucket/prefix. Enable Block Public Access/equivalent, deny non-TLS requests, disable public ACLs, require encryption, enable versioning and separately administered replication/backups. Grant the app only PutObject/GetObject/GetObjectVersion/DeleteObject (and version delete for failed uploads if permitted) on `evidence/*`, plus minimal bucket health permission (`HeadBucket` generally requires ListBucket). Restrict ListBucket to the bucket/prefix where supported; no browser credentials or bucket listing route exists. Use separate backup and administrative identities. Staging acceptance must verify unsigned requests are denied and real put/get/version/delete/health permissions and TLS trust work with the selected provider.

Files are limited to 2 MB. JPEG/PNG/WebP images are actually decoded, pixel/page limited, auto-oriented, resized if needed and re-encoded as WebP, stripping EXIF/GPS. Mislabelled executables, malformed images, unsafe filenames/path traversal and disallowed types are rejected. PDF receipts are permitted for expenses/purchases only, require PDF framing, reject obvious active content and always download as attachments under a sandbox CSP. This conservative PDF check is **not an antivirus or full PDF parser**; do not treat uploaded receipts as trusted documents. Consider an isolated malware scanner/CDR pipeline before broadening uploads or accepting untrusted public uploads.

Metadata records original filename and input size, canonical type/stored size, SHA-256, safe random object key, provider/version, creator/time, parent and storage state. Downloads require session + record authorization, verify stored bytes/integrity, return no-store/nosniff, and audit access. Caretakers see assigned-room/booking evidence and their own expense receipts; purchases remain financial-access only. Existing `/api/evidence/:id` and `/api/attachments/:id` URLs keep working with legacy bytes. New `/api/files/:id` never serves an unlinked, staged, failed or archived file. Opaque IDs complement authorization; they do not replace it.

Purchase, booking and room detail pages support new private evidence. Existing damage/inspection/expense forms use the same storage service. Completed inspection/reviewed-expense evidence remains immutable. New purchase receipts append supporting evidence without changing receiving or approved financial records.

Owners can use `/settings/storage` to archive/restore eligible evidence with password confirmation. Historical damage, inspection and financial files cannot be archived here. Only unlinked READY files or evidence on cancelled stays (without legal holds)/inactive rooms is eligible. Archive is reversible and retains bytes; no ordinary-user hard-delete endpoint exists.

Existing blobs need not be migrated immediately. For controlled batches, set `FILE_MIGRATION_ACTOR_EMAIL` to an active Admin and `FILE_MIGRATION_CONFIRM=MIGRATE_PRIVATE_FILES`, then run `npm run files:migrate`. It processes up to 25 legacy photos and 25 operational attachments per run, retains original bytes and links only after successful storage/transaction commit. Failed invalid legacy files remain readable from the original route; review counts before repeating. Do not directly mutate metadata/object keys to move files.

Uncertain/failed uploads remain tracked. With `MAINTENANCE_CONFIRM=EXPIRED_SECURITY_AND_UNLINKED_FILES`, `npm run maintenance` retries cleanup of unlinked STAGED/FAILED uploads older than a day (100 per batch), expires old rate buckets/sessions and recovery tokens. It never purges READY/ARCHIVED evidence, operational records or audit logs. If versioning is enabled, an ambiguous failed PUT may leave a historical object version; review these using a privileged reconciliation process. Never configure an aggressive object expiration lifecycle that can erase referenced historical evidence.

## Security, privacy and monitoring

All services retain server-side role checks; UI visibility is supplementary. Server actions require Origin validation, authenticated actors, Zod validation, and per-user shared mutation limits. Public forms bound actual bytes, not just Content-Length. PostgreSQL limiter buckets work across instances; rotate/retain the HMAC key consistently across instances. Failed database access fails closed. Defaults: login IP 30/15m in production (300 in development), login account 10/15m, reset IP 10/15m, reset account 5/15m, reset submissions 15/15m, uploads 60/user/5m and mutations 120/user/minute. Adjust documented variables to observed caretaker use. Limits are fixed windows, so boundary bursts are possible; supplement with ingress DDoS/body/concurrency limits.

The reverse proxy must strip client-supplied `x-cabin-client-ip`, derive a verified client IP, overwrite that header, preserve canonical Host and be the only app ingress. Never trust arbitrary X-Forwarded-For. Without trusted proxy configuration, local requests share an anonymous IP bucket. Preserve these headers for multi-instance throttling. Apply an ingress body limit of 3 MB, lower on login/recovery endpoints.

Every HTML response has a fresh nonce CSP with strict dynamic scripts, self-hosted styles/assets, no unsafe-inline or wildcard sources, no frames/objects/base URL, and same-origin forms. Development HMR alone permits unsafe-eval. `strict-origin` referrers exclude path/query (including reset tokens) while preserving Origin on native Chromium form submissions; Origin:null remains rejected. Other headers enforce nosniff, DENY frames and restricted camera/microphone/geolocation/payment. HSTS is enabled in production after HTTPS is mandatory; subdomains/preload are deliberately not assumed. No arbitrary redirect target is accepted. Login/recovery/private responses are not cacheable. Redact query strings, cookies, authorization headers and form bodies in reverse-proxy/APM logs, especially reset URLs.

Security events include login/failure/throttle/lock/logout, reset request/completion, password/user changes, file upload/access/archive/restore and administrative backup/recovery. Existing financial approval/edit/receiving/checkout events remain. Ordinary users cannot edit activity logs; only Admin reads them. Historical audit records are retained. New booking creation/edit logs include field names/counts/references instead of duplicating mobile/email/free-text notes. Existing historical logs are not rewritten.

Guest contact fields remain optional. Owners can archive contact visibility on closed stays, restore it or set/release a legal hold, with password confirmation. Managers no longer see archived contact details; Owners retain access for legitimate recovery. Archive does not erase guest names, financial references or history and is not a complete anonymization feature. Do not put card numbers, government identifiers, medical data or unnecessary personal information in notes/files. The system does not process/store card payments; paid statuses are operational records.

Owner retention policy recommendation: review operational guest contact access after 90 days from departure; retain only what remains necessary; retain damage/inspection evidence through disputes; retain financial/audit history for the locally applicable accounting/legal period; honour legal holds. Review backup retention separately. These are operational defaults to agree with the owner/legal adviser, not legal guarantees. This phase provides reversible archive and documented review, **not automatic personal-data deletion**. Formal anonymization/export-right workflows and external immutable audit sinks are deferred.

`/api/health/live` reports process liveness without DB access. `/api/health/ready` and `/api/health` verify database and storage health (storage success cached for five seconds). They return only status/request ID, no credentials, paths or stack traces. Restrict monitoring probe traffic at ingress. Structured error events contain timestamp, severity, request ID, allowlisted context/error class/code and a stack fingerprint, never raw messages, URLs/bodies, guest/financial data, passwords or tokens. UI failures have friendly retry guidance; framework production errors do not expose stacks. Unexpected action, auth, database, storage and request failures use the same logger.

Optional `MONITORING_PROVIDER=webhook`, HTTPS `MONITORING_WEBHOOK_URL` and optional bearer `MONITORING_TOKEN` send this safe event shape to a provider-neutral collector with bounded timeout. Default is console-only. Set alerts on readiness failures, error rate, login lockouts/throttles, backup age/failure and storage cleanup backlog. Deliveries are best effort, not a durable queue. Monitoring transport failures never undo committed business data. Do not enable full request/SQL argument collection in external agents. Audit/anomaly events also remain in the database for Owner review.

## Backup and restore

Use provider-managed encrypted daily snapshots **and continuous WAL/PITR where available**. Suggested starting objectives: RPO 15 minutes/RTO 4 hours, daily full backup, 14 daily/8 weekly/12 monthly copies, reviewed against cost and applicable retention obligations. Store independently encrypted off-site copies with separate administration, object versioning/replication and deletion protection. Only designated recovery operators access backups; keep encryption keys separately in a recoverable secret manager, rotate/version keys and rehearse access with a second authorized operator. There is no automatic backup scheduler in the web app; configure a private scheduled job and alert on its last verified result.

Helpers require PostgreSQL 17-compatible `pg_dump`/`pg_restore` executables and private release tooling (`npm ci`). Passwords are passed in child environment, never command arguments. `DIRECT_DATABASE_URL` is preferred for source connections. The database backup role needs export-snapshot/read permissions and audit INSERT; a restore operator needs privileges only on its isolated target.

1. Create a `0700` backup directory and a separate `0600` file containing 64 hex characters from a cryptographic random generator. Set `BACKUP_DIRECTORY`, `BACKUP_KEY_FILE`, and the source database configuration.
2. Run `npm run db:backup`. It holds a read-only repeatable-read exported snapshot while taking a custom-format dump and all-table row counts/object-version/SHA manifest. Both dump and manifest are AES-256-GCM encrypted with independent IVs; files are `0600`. Completion is audited without credentials or guest content. Securely copy the encrypted pair off-site and retain the associated key version separately. Do not lose the manifest.
3. For a rehearsal or incident, provision a **new, empty, isolated** PostgreSQL database/role. Set `BACKUP_PREFIX` to the backup path without suffixes, `RESTORE_TARGET_DATABASE_URL`, the matching key file and exact `RESTORE_CONFIRM=RESTORE_TO_EMPTY_DATABASE:<target database name>`.
4. Run `npm run db:restore`. It refuses an identical source identity, wrong confirmation and any public tables/routines/sequences. It verifies manifest authentication, encrypted dump SHA and full GCM authentication **before** executing SQL. Restore uses a single transaction, exit-on-error, no owners/ACLs and never --clean/--create. All table counts are compared with the consistent manifest before success, then restoration is audited. A count mismatch or interruption means **do not cut over**; investigate only the isolated target.
5. Verify migrations, login/admin recovery, inventory/linen totals, decimal expenses/charges, booking/inspection history, role restrictions and representative legacy/object-store attachments in the isolated service. Verify the manifest's object key/version/size/hash records against an independently restored private bucket (provider tools/identity), including unsigned access denial. Database restore alone does not restore remote objects. Database-backed legacy/development blobs are in the dump.
6. Have the authorized operator explicitly approve any eventual production cutover. Preserve the prior database and rollback plan. This phase never automatically replaces the application database or switches traffic.

The helper detects identical host/port/database names including loopback aliases, but cannot prove two DNS names/proxies are not the same underlying cluster. Use an independently provisioned target and verify its identity/access boundaries. Target restore coordination uses an advisory lock shared by these helpers; nobody else should create objects/write there during restore. CLI dump decryption uses a private temporary file that is removed in a finally block; use encrypted temporary disks and least privilege. Current manifest/hash verification reads encrypted dump bytes in memory: use native provider-managed encrypted snapshots/PITR or extend the helper with streaming hashing/manifests for large databases rather than risking operator memory exhaustion.

S3 metadata in the dump identifies immutable object keys and versions. Keep object versions/backups at least as long as referencing database backups. Do not overwrite/expire referenced READY/ARCHIVED objects. Encrypted database dumps alone are insufficient once S3 is enabled. Rehearse full DB + object-store recovery at least quarterly and after schema/storage changes, recording duration, validation and missing permissions. The local drill uses `PG_TOOL_CONTAINER` only to access existing PostgreSQL tools inside the local development container; that wrapper is rejected in production.

## Deployment preparation and final acceptance

Use Node 24 LTS, `npm ci`, `npm run build` and `npm start` for a private Node service. `npm start` loads an optional local `.env` and defaults to loopback; use `APP_BIND_HOST` only for controlled container/service ingress. The standalone Docker image runs a non-root Node 24 process, with a dedicated build stage and no runtime dev tools. Run migrations/admin/backup from a separate private tooling job. Build with `docker build -t cabin-operations .`; in this managed cloud environment supply its CA using `--secret id=proxy_ca,src="$CODEX_PROXY_CERT"`. Keep platform proxy settings and TLS verification; never bake session CA/credentials into images. No image was publicly pushed and no service publicly deployed. Phase 5 adds an explicit `runtime-entry.mjs` that validates configuration before importing `server.js`; always use that entry point.

Choose a domain later. Configure DNS and a trusted TLS certificate on an ingress that redirects HTTP to HTTPS, strips client IP headers, sets canonical Host, forwards to private app port 3000, limits bodies/requests, and never caches staff HTML/API responses. Set `APP_URL` to exactly that HTTPS origin. Verify Secure cookies, CSP, HSTS and reset links from that actual domain. Do not publish raw Node/PostgreSQL/S3 admin ports. The container needs no persistent filesystem volume; PostgreSQL and private object storage are the durable stores. Mount private CA/keys read-only if required. Docker filesystem/logs are not a backup.

Before final production deployment:

- Apply reviewed migrations to an isolated staging database; verify status/drift and indexes/check constraints.
- Supply real scoped S3/SMTP identities and TLS/proxy configuration. Run `production:check`; verify actual email delivery and private bucket put/get/version/delete permissions, anonymous denial, backup replication and representative downloads.
- Bootstrap a unique Admin into an empty production database, validate recovery access, remove temporary password files and confirm no demo users/guests.
- Run lint/typecheck/unit+DB/build/HTTP/mobile tests against synthetic isolated staging data. Do not run mutation-heavy test fixtures on live production.
- Test readiness/storage/database outages, 429 feedback, temporary lockout, reset single use/session revocation, and no credential/token content in ingress/application/monitoring logs.
- Schedule backups/maintenance, restore DB and attachments into separate targets, record RPO/RTO, test operator recovery, configure alerts and get operational cutover approval.

Known deferred work: full TOTP MFA, durable SMTP/monitoring queues, full antivirus/PDF CDR, large-database streaming backup enhancements, real provider staging verification, formal guest anonymization/deletion workflows and immutable external audit replication. None is silently claimed to be active. See `phase4-verification.md` for the actual checks and remaining deployment gates.
